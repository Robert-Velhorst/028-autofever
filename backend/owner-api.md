# Local owner connection

This is an opt-in development path, **not deployed production authentication**. Start the loopback listener with `--with-owner` and visit `/owner`. Without this option all owner routes and assets are absent. `/help` remains the separate recipient page. The same local-server restrictions in [README](README.md) apply: no port forwarding, public reverse proxy or production credentials.

The same owner interface and capability contract are also used by the separate [hosted entry point](../deploy/README.md), which adds authenticated proxy checks and rate limits. That path is tested locally but not deployed. The local instructions below do not authorize exposing the development listener.

## Setup and authority

A trusted operator can now use the [private setup CLI](provisioning.md) to initialize a new dedicated store and provision owner access into a private credential file. Interrupted enrollment is explicitly resumable using that same file; it does not print the code or create a second owner on replay. Only the capability hash and an encrypted enrollment audit are stored in the database. `Store.create_owner()` remains a lower-level trusted API that returns the raw capability once; callers are responsible for persisting it safely. Transfer only the capability privately. Do not put it in a URL, Git, shared logs or screenshots. The browser's **Instellingen → Lokale server koppelen** form checks it against the configured same-origin server before storing it. No email/password account or recipient login is introduced. Nontechnical onboarding/transfer and recovery remain required production work.

Choose a visible helper-link lifetime of 1–168 hours at setup. Changing it affects new episodes only. The HTTP/core contract accepts an explicit 60–604800 seconds. The capability is stored in a separate encrypted IndexedDB record, using the existing browser key; that key is on the same device. This does not protect an unlocked browser, a compromised device or same-origin script execution. A trusted operator can now [replace or revoke a retained owner credential](owner-access.md), preserving server history and denying subsequent requests with the old code. This does not erase data already displayed or implement a self-service device-loss recovery flow. Browser profile backups deliberately exclude the connection record and pending server operation; restoring a profile backup does not mutate, cancel or recover an existing server episode. Do not clear browser storage when an action's outcome is unknown.

The server injects a same-origin connection module into the existing HTML. Exact hashes authorize its existing inline script; the owner page permits inline styles required by the existing layout. The recipient page retains its stricter no-inline-script/no-inline-style CSP. Both pages are one origin; this is not a cross-origin security-isolation claim. The source preview remains usable standalone, with no networking or server activation when the connection module is absent.

## One-press activation and uncertain outcomes

1. Prepare contacts and save the default profile in the existing editor. Drafts remain separate.
2. **Ik ben ziek** reads the saved record and refuses a detected stale-tab revision. There is no second confirmation.
3. Before making an HTTP request, store a random command identifier and immutable selected profile/contact payload in the encrypted connection record. A conflicting connection revision fails before sending.
4. The server validates the full profile, snapshots the original preparation, and atomically creates the episode, help tasks, recipient capabilities and outgoing jobs.
5. Record success only after a successful server response. Unknown/network outcomes preserve the same command and payload in the encrypted connection record across reload. While the owner page remains open, a restored connection triggers at most three retries with 1-, 5- and 15-second delays, always using that same idempotent command; definitive validation/conflict responses stop automatic retries. **Uitkomst controleren** remains available for a manual retry. If the page is closed while offline, reopen Autofever to resume. There is no service-worker/background sync, delivery guarantee or success state based only on a network event.
6. **Serverstand ophalen** reads the authoritative last episode, acknowledgments, help claims/completion and outgoing queue states. It does not send messages. There is no automatic polling/push subscription yet; labels explicitly describe the last checked state.

One recipient currently needs exactly one Email, SMS or WhatsApp channel. There is no arbitrary first-channel selection, invented Push address, or automatic fallback. Multiple selected channels and Push fail before activation. International phone numbers require `+countrycode`; formatting spaces, dots, parentheses and hyphens are normalized without inventing a country code. This limitation does not remove multichannel/fallback from the product scope.

All supported preview fields are preserved: profile ID/name, general and per-person messages, recovery text, expected return, check-in interval, selected recipient order, selected contacts, and each task's ID/title/description/helpers/time/repeat/backup. Unknown fields are rejected rather than ignored. Task descriptions reach only assigned recipients. Preparation and all contact destinations are visible only through owner access, not recipient APIs. Repeat and backup preferences are stored but not scheduled/executed. Check-ins are now calculated from the saved interval and active episode: the owner sees an overdue check-in only upon opening or refreshing Autofever, and can confirm it to begin the next interval. This does not send a push, email, SMS or helper message. [Explicit updates](updates.md) can now be queued from the server-connected owner page for selected already-informed recipients. The standalone preview's update editor remains local-only.

## Recovery and cancellation

**Ik ben hersteld** opens a review step before closing: the owner may edit the recovery text and select a subset of recipients whose initial illness notice was positively accepted by the sender. No new recipient can be added. Acceptance is not delivery or reading. The chosen text and recipient IDs are encrypted locally before submission; the server validates eligibility and atomically closes the episode and queues exactly that subset. Lost responses replay the same encrypted operation without duplicate notices. **Gebeurtenis annuleren** closes without recovery notices. Both invalidate recipient access through episode state and close unfinished tasks.

The closing request is persisted before submission. A lost response is reconciled against the latest episode after reload, or the identical terminal operation can be retried. A new illness episode is refused while prior outgoing work is queued/in flight/uncertain. Closing while a send is in flight or uncertain is also refused. A [private operator tool](reconciliation.md) can settle an uncertain attempt using externally verified provider evidence; the owner bearer cannot invoke it. Refreshing then shows the resulting ordinary queue state. Unresolvable uncertainty and a nontechnical support flow remain required work; never bypass the guards by editing SQL statuses. A definite 409 does not retain a misleading successful operation.

## HTTP contract

All routes require an owner bearer capability, exact Host, same-origin mutation requests, no query strings and no cookies. An unknown, recipient or other-owner capability cannot read or close an owner's record. No public owner creation or sender-dispatch routes exist. [OpenAPI](openapi.yaml) includes the transport shapes.

| Route | Method | Input | Success |
| --- | --- | --- | --- |
| `/api/v1/owner/episode` | GET | No body | `{data: null}` or most recently created own episode, including terminal state |
| `/api/v1/owner/retention` | GET | No body | `{data: {retention_days}}`, with `null` meaning disabled |
| `/api/v1/owner/retention-setting` | POST | Exactly `{retention_days}`; `null` disables, otherwise integer 1–3650 | 200 with saved per-owner live-history retention policy |
| `/api/v1/owner/export` | GET | No body | Complete owner-scoped server history in an authenticated, `no-store` JSON response |
| `/api/v1/owner/data-deletion` | POST | Exactly `{confirmation: "DELETE_MY_SERVER_DATA"}` | 200 with `deleted_episodes`; replay is safe and returns zero after the first deletion |
| `/api/v1/owner/episodes` | POST | Exactly `command`, `profile`, `contacts`, `link_ttl` | 200 with the episode, both on first activation and idempotent replay |
| `/api/v1/owner/episode-closures` | POST | `episode_id`, `state`, `recovery_message`; optional `recovery_recipients` on recovery | 200 with updated episode; recovery recipients must be a nonempty subset of recipients whose initial illness notice was accepted; cancellation requires a null message and no selected recipients |
| `/api/v1/owner/episode-updates` | POST | Exactly `episode_id`, `command`, `message`, `recipients` | 200 with updated episode; exact-content retry creates no duplicate jobs |

An episode response has `id`, `state`, immutable `snapshot`, `recovery` (the chosen message and selected recipient IDs derived from encrypted recovery queue entries, or `null`), `notifications` (`id`, `recipient`, `kind`, `status`, `attempts`), `recipients` (`id`, `acknowledged`) and `tasks` (`id`, `state`, `claimant`, `declined_by`). Never raw recipient links, sender receipts, owner capabilities or database details. An owner may see the identities of their own helpers; another recipient may not.

The optional retention policy defaults off and is stored encrypted per owner. When the operator enables the daily host timer, the bounded purge deletes only closed episodes older than the selected period and skips active, queued, sending or uncertain work. See [retention behavior and host setup](retention.md); this policy does not expire off-host or operator backups.

The export route returns `{data: {format: "autofever-owner-export", version: 1, exported_at, episodes}}`, including each episode's creation time, snapshot, chosen recovery message and recipients (when a recovery notice was queued), updates, check-in state, helper responses and notification statuses. Recovery content is derived from the existing encrypted queue payloads; no second persistent copy is created. For active and closed episodes it preserves the latest check-in confirmation; closed episodes have `due: false` because no check-in is actionable after closure. This is not the local profile backup and cannot be restored into the running service. The owner page derives an AES-256-GCM key from a passphrase using PBKDF2-SHA256 (600,000 iterations), encrypts the JSON in the browser, then offers a `.afexport` file. The JSON envelope has `format`, `version`, `kdf`, `iterations`, `salt`, `iv` and `body`; the binary fields use standard Base64, the salt is 16 random bytes, the IV is 12 random bytes, and `body` contains the Web Crypto AES-GCM ciphertext and authentication tag. The passphrase must be at least 14 characters; it is neither stored nor sent to the server. Treat the file and passphrase as sensitive; keep the passphrase separately. The authenticated API response necessarily contains plaintext in the browser's memory while encryption runs, so use only the configured trusted HTTPS origin for hosted use.

The deletion route removes **live server** records for that owner in one transaction: all episodes and contact snapshots, helper capabilities/responses, tasks, queue jobs, check-ins, updates and episode reconciliation metadata. Queued messages are removed and cannot later be dispatched; an already submitted message cannot be recalled. To avoid erasing an unresolved send outcome or allowing a provider call to continue after deletion, the route uses the shared delivery lock and returns 409 if delivery is active or any owner job is `sending` or `uncertain`. Resolve that provider outcome before retrying. The owner capability is retained, so local profiles and access remain usable. The separate **Lokale gegevens wissen** control clears the current browser's IndexedDB vault and connection; it does not erase server history. The UI explains that downloaded backups, operator-held database backups and copies already delivered to helpers are outside these operations. This is logical deletion from live application records, not a guarantee of physical media overwrite. Off-host backup expiry and deletion are separate unfinished operator tasks.

Activation bodies have a 2 MiB limit, updates 32768 bytes and other mutations 8192 bytes. Shared error codes: 400 invalid/unsupported input, 403 host/origin mismatch, 404 unavailable access, 405 wrong method, 409 conflicting state, 413 size, 415 non-JSON, 503 generic internal/temporary error. Error text does not interpolate input or exceptions. No production rate limiter is implied by the local listener; HostedApp adds its documented quotas.
